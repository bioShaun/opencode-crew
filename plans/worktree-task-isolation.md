# Crew 按任务隔离并行执行方案

记录日期：2026-10-31

状态：阶段 0 的能力调查与受限验证已完成，存在 FAIL 与 NOT_TESTED，不是全部通过。详见 [阶段 0 最新验收](worktree-stage0-results.md)。用户已批准受限阶段 1 的设计与实现，实施以 [阶段 1 契约](worktree-stage1-contract.md) 为准；阶段 2 尚未批准。

## 1. 目标与决策

允许 Root 将明确独立的实现任务交给多个 engineer，在各自 worktree 中并行执行；Root 核查结果、串行整合并验证整合后的行为。

采用按任务显式启用的隔离方式，不让所有 subagent 默认创建 worktree：

- 只读探索：继续使用原生 subagent，不创建 worktree。
- 单个明确的小实现：原工作区保持单写入者。
- 多个独立、可分别验收的实现：考虑 worktree 并行。
- 紧密耦合的接口改动：先统一契约，必要时串行。
- 有共享数据库、服务或其他外部副作用的任务：先解决环境隔离，不因创建了 worktree 就直接并行。

核心原则：任务拥有 worktree，会话在任务内执行；并行执行，串行整合。

## 2. 已核对的现状与证据边界

- `src/index.ts` 使用 `Plugin.define` 注册角色与 `/crew`，没有任务会话创建、worktree 管理或自有调度器。
- `src/index.ts` 的 architect 路径权限以 `ctx.location.directory` 为基准；跨目录会话中的规则是否正确生效需要实测。
- `README.zh-CN.md` 的“并行现状”明确：同一 cwd 一个写入者；没有自动 worktree、队列、锁、并发上限、依赖 DAG 或冲突检测。
- 项目声明已验证的 OpenCode 版本为 2.2.3；在线 V2 文档可能继续更新，不能代替目标安装版本的运行验证。
- 官方 V2 文档提供 `ctx.worktree.create/list/remove/refresh` 以及 `ctx.session.create/move/prompt/wait/interrupt` 等基础能力。
- 本轮可见的原生 `subagent` 工具未暴露 directory/worktree 参数。不能由 worktree API 的存在推断原生 subagent 已支持自动目录隔离。
- 当前没有实测证据证明双工作区会话的隔离、中断、恢复或整合流程可用。

## 3. 非目标

第一版不实现：

- 所有 subagent 自动隔离。
- 自动拆任务、依赖 DAG 或完整调度平台。
- 自动解决冲突、自动合并。
- 自动提交、推送。
- 自动强制清理工作区。
- 容器级运行环境隔离。

不复制第二套 engineer/reviewer 角色定义，沿用 Crew 既有角色与模型配置。

## 4. 工作流程

1. Root 核对主工作区与固定基线，确认任务可独立验收。
2. 每任务准备一个 worktree 与任务会话。
3. engineer 在各自工作区并行实现、自验证。
4. 写入结束后固定待审查结果，Root 核对实际差异与证据。
5. 按风险安排 reviewer 检查对应任务工作区的稳定结果，不另建遗漏未提交修改的副本。
6. Root 串行整合，每次做必要检查，最终做整合后回归。
7. 确认成果保留与活动执行状态后，按明确授权及清理条件移除工作区。

## 5. 阶段 0：验证宿主能力（调查与受限验证已完成）

以下保留原验证契约。实际结果以 [最新验收报告](worktree-stage0-results.md) 为准：双 build 会话隔离通过；当前 Crew 角色加载已验证；直接 `session.shell` 中断失败；模型同步前台 shell 单例中断通过；记录恢复不等于自动续跑。不能将未测项目视为通过。

### 范围

只做最小可撤回验证，不修改 Crew 业务实现，不开发完整任务管理层。开始前核对实际安装版本、适用指令及工作区基线；证据放在项目内独立目录，执行前确定具体路径。

先调查原生 subagent 是否存在可用的指定目录入口；没有时，验证插件管理独立任务会话的路径。后者不能未经验证就宣称具备原生 subagent 的父子关系、通知及取消语义。

### 验证项目与验收口径

| 项目 | 验证内容 | 通过标准 |
| --- | --- | --- |
| 目录绑定 | 会话目录、文件工具路径、shell cwd | 三者指向目标 worktree，实际读写一致 |
| 配置与权限 | 目标目录项目配置、角色和路径规则 | 按目标目录正确加载；不把 cwd 当作安全沙箱 |
| 双会话隔离 | 两个受控任务并行读写 | 各自修改只出现在本工作区，主目录及对方目录不变 |
| 结果追踪 | 任务、会话、基线、目录映射 | 可用真实记录关联并回收结果，不仅依赖模型声明 |
| 完成与中断 | 会话状态、运行命令与残留进程 | 能区分会话结束与命令停止；无法确认停止时不清理 |
| 成果保留 | 中断或失败后的修改 | 修改可检查，不自动提交、删除或覆盖 |
| 恢复 | 重载后重新发现任务 | 可找回已有会话和 worktree，不重复启动 |

### 约束与停止条件

- 使用两个临时验证 worktree、两个小任务，记录创建前后基线和差异。
- 不提交、不推送、不自动强删；清理不能损失未验收成果。
- 不影响既有任务或重启健康服务；涉及重载时先确认影响范围。
- 目录绑定或生命周期控制不可靠时，停止自动化推进，交回证据和限制；保留手工 worktree + 独立会话作为替代方案。
- 不把工具错误、模型不可用、证据缺失或 BLOCKED 当作通过。

### 交付

逐项验证结论、证据索引、失败限制、推荐采用的会话路径，以及是否值得进入阶段 1 的建议。进入阶段 1 前再次确认范围。

## 6. 阶段 1：薄的隔离任务层（已批准受限版本）

本节保留初始规划；已冻结的首版范围以 [阶段 1 契约](worktree-stage1-contract.md) 为准：仅绑定预先准备的干净 worktree，提供 start/status/stop；不自动创建、重试、整合、释放或清理。停止安全始终未确认，需外部人工核实。

阶段 0 通过后再确定接口、文件边界与测试设计。以下为逻辑责任，不是已存在的工具或已冻结的 API 名称。

### 最小操作

- 启动隔离任务：检查条件、创建 worktree、建立并绑定会话、发送自包含任务包。
- 查看任务：返回状态、基线、会话、目录及验证证据索引。
- 停止任务：请求中断、确认状态、保留成果。
- 清理任务：检查活动执行、修改及保留条件，再安全移除。

不提供一键自动合并。任务管理与现有角色注册在逻辑上分离，优先复用宿主原生能力。

### 最小持久化记录

任务 ID、目标与允许修改范围、项目、固定基线、worktree 目录、会话 ID、角色、状态与错误、验证证据位置、整合和清理信息。

避免重复启动与状态更新竞态；不能仅使用插件内存保存映射。

### 状态语义

准备中 → 执行中 → 待验收 → 已整合；另有已停止、失败。

清理信息单独记录。会话执行结束、子代理声称完成、Root 已验收、结果已整合是不同事实，不能合并为一个成功状态。具体转换与恢复规则在阶段 1 设计时确定。

### 保守约束

- 同一项目最多两个隔离写任务，作为试运行上限，不代表宿主限制。
- 每个 worktree 同时最多一个写入者。
- 启动时使用同一已确认基线。
- 主工作区存在未提交改动时，第一版拒绝自动启动；不偷偷 stash、提交或复制现场。
- 不复制整个主目录，不默认复制 `.env`，不默认软链接可写依赖或共享输出目录。
- 初始化步骤显式列出；失败如实记录，不报告已启动。
- 不自动提交、推送或强制清理。

## 7. 阶段 2：真实双任务试运行（待后续批准）

选择两项边界清楚、验收便宜且不同时修改公共入口的独立行为改动。

1. 两任务从相同基线启动。
2. 分别先写测试并记录因目标行为缺失而失败的红灯，再实现并记录绿灯。
3. 停止写入后检查实际差异与验证证据。
4. Root 串行整合；每次整合做必要检查，最终执行完整必要回归。
5. 检查是否存在工作区外意外输出。
6. 清理前确认成果已保留且无活动执行。

评估并行节省是否超过初始化、审查、整合和恢复成本；通过后才考虑提高并发、初始化模板或冲突预警。

## 8. 结果整合契约

默认不提交时，交付固定基线、完整改动快照和测试证据。

- 不能仅用普通 `git diff` 代替完整成果：必须覆盖未跟踪新增文件、修改和删除。
- 不包含密钥、依赖、构建缓存或无关临时产物。
- 整合前检查改动范围及主工作区是否偏离预期状态。
- 冲突时停止，由 Root 决定修复、基于新基线返工或放弃结果，不自动覆盖。
- 快照格式与应用机制需后续明确设计和测试，不临时使用无保护的目录复制代替。

## 9. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 各自测试通过，整合后失败 | 任务独立性审查、串行整合、整合后回归 |
| 会话中断但命令仍运行 | 实测中断语义，未确认停止前拒绝清理 |
| 清理丢失未验收成果 | 默认保留，有修改时拒绝直接清理 |
| 共享数据库、端口、缓存冲突 | 显式检查外部副作用，不将 worktree 视为完整环境隔离 |
| 重载丢失任务或重复启动 | 持久化映射与恢复检查 |
| 跨目录读写或 Git 公共状态修改 | 范围与权限检查；承认 worktree 不是 OS 沙箱 |
| 并行收益被整合成本抵消 | 从两个独立任务试运行，不追求默认高并发 |

最可能的失败原因是任务不独立，而非 worktree 创建失败。小型、紧密耦合任务继续单写入者通常更划算。

## 10. 执行与资源规则

- 默认不提交、不推送。
- 临时及中间文件放项目内子目录或 `/project/tmp`，禁止 `/tmp`；同样约束子进程与子 agent。
- 预计超过一分钟、超过 2G 内存或大量读写 `/data_0` 的重活，首次启动前读取 `~/.config/agents/slot.md`，执行 `slot audit`、`slot status` 并记录项目日志，再通过 `slot <io|cpu|gpu|nf> -- <cmd>` 提交。
- 同一 cwd 仅一个写入者；Root 与 engineer 不同时修改。
- 阶段 1 的行为变更必须测试先行，保留有效红灯与实现后绿灯证据；语法、导入错误不算有效红灯。
- 子任务交接包含 Goal / Scope / Decided / Approach / Acceptance / Check、适用规则和证据位置。

## 11. 放弃的方案及重新考虑条件

- 所有 subagent 默认隔离：只读及小任务收益不足；若宿主提供低成本、成熟的原生隔离模式，可重新评估。
- 立即开发完整调度器：宿主行为尚未验证，复杂度过高；只有薄层在真实任务中证明价值后才扩展。
- 默认 clone 或容器：当前成本不匹配；需要 Git 管理隔离或数据库、服务等运行环境隔离时再考虑。
